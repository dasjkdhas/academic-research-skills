# AMeDAS 觀測 vs JMA 預報 — 該用哪個作預測輸入？

## 🎯 您的問題（精準解讀）

> 「用 AMeDAS 數據跟當天氣象廳數據直接預測哪個更合理？」

這是方法論的核心問題。讓我先**釐清概念差異**，再用實驗回答。

---

## 📚 兩種資料的本質差異

| 維度 | **AMeDAS 觀測** | **JMA MSM/GSM 預報** |
|------|----------------|---------------------|
| 本質 | 地面測站「**已發生**」的真實測量值 | 數值模式「**未來會發生**」的預測值 |
| 取得時間 | 事件發生後即可取得 | 事件發生**之前** 12-39 小時即可取得 |
| 對「現在時刻 t」 | 直接觀測 | 過去某時 t-Δ 對 t 的預報 |
| 對「未來時刻 t+24」 | **不存在**（時間未到） | **存在**（今天發布的明日預報） |
| 誤差來源 | 儀器精度（極小） | 模式誤差（MAE 0.76°C 等） |
| 空間覆蓋 | 站點稀疏 | 5km × 5km 格網 |
| 更新頻率 | 10 分鐘 | 3 小時 (MSM) / 6 小時 (GSM) |

**關鍵啟發**：兩者**不是替代關係**，而是**互補關係**。

---

## 🚨 部署現場的硬約束

```
今天 17:00 (預測時間 T)
   ↓
我要預測「明天每小時 b00」(T+1 ~ T+31 小時)
   ↓
問：明天 14:00 的氣象變數從哪來？

答案：
  ❌ 明天 14:00 的 AMeDAS 觀測 → 還沒發生，根本不存在
  ✅ 今天 JMA 發布的「明日 14:00 預報」→ 唯一可用
```

**結論**：對於「未來時段」的預測輸入，**只能用 JMA 預報**。AMeDAS 在這裡**根本不是選項**。

---

## 🧩 但模型有兩段時間軸 — 滯後特徵 (lag) 怎麼辦？

預測「明天 14:00 的 b00」時，模型需要兩類特徵：

```
        T-168h    T-24h    T(now=今天17:00)    T+21h=明天14:00
          |        |             |                     |
        [一週前]  [昨天]      [現在]                 [預測標的]
       ←─── 滯後特徵 (lag features) ───→  ←── 預測時段 ──→
```

**滯後特徵的氣象變數** 可以用：
- (i) **AMeDAS 觀測** (e.g., 「今天 14:00 的真實溫度」) — 因為這是**已過去的時間**，有實測 ✓
- (ii) **JMA 對該時刻發布的預報** (e.g., 「昨天 JMA 對今天 14:00 的預報」) — 也可以用

兩者選哪個？關鍵權衡：

| 策略 | 訓練 | 部署 | 優缺 |
|------|------|------|------|
| **A. 全 JMA 預報** (目前做法) | 預報 | 預報 | ✓ 訓練/部署一致；✗ 訓練信號含模式誤差 |
| **B. 全 AMeDAS 觀測** | 觀測 | 部署時用觀測(過去)+預報(未來)→ **特徵分布錯亂** | ✗ Domain Shift |
| **C. 混合**：lag 用觀測、未來用預報 | 觀測 + 預報 | 觀測 + 預報 | ⭐ **最佳：訓練信號乾淨 + 部署一致** |

## 🧪 三架構實證對比結果

**實驗設定**：相同模型 (LightGBM, 同超參、同 seed)、相同 split (50/15/15/15 walk-forward CV + 70/30 holdout)、相同 40 個 day-ahead-safe 特徵，**只改變氣象變數的資料來源**。

樣本：2025-07-20 ~ 2025-10-26 共 2,145 小時。

### 3-fold Walk-forward CV 結果

| 架構 | 氣象資料來源 | CV MAE (kW) ↓ | CV R² ↑ | CV MAPE (%) ↓ |
|------|------------|--------------|---------|---------------|
| **A. Obs-only** | 過去+當下都用觀測 (ERA5) | **59.4** ± 19.4 | **0.892** | 7.75 |
| **B. Forecast-only** *(目前部署)* | 過去+當下都用 JMA MSM 預報 | 64.6 ± 20.6 | 0.873 | 8.29 |
| **C. Hybrid** | lag 用觀測，當下用 JMA 預報 | **59.5** ± 16.0 | 0.888 | **7.67** |

### 70/30 Holdout 結果

| 架構 | MAE (kW) ↓ | RMSE (kW) ↓ | R² ↑ | MAPE (%) ↓ | Day-Peak MAE (kW) |
|------|-----------|-------------|------|-----------|-------------------|
| **A. Obs-only** *(理論上限)* | **50.7** | **66.3** | **0.915** | **6.96** | **78.6** |
| **B. Forecast-only** | 59.7 | 78.0 | 0.883 | 7.93 | 92.4 |
| **C. Hybrid** | 54.0 | 70.2 | 0.905 | 7.28 | 84.9 |

### Day-Level SDR Call 決策準確度

三種架構 **完全一致**：TP=11, FP=0, FN=1, TN=16, F1=0.957。

**這代表**：在「日級別 SDR 啟動決策」這個業務指標上，三種架構**沒有差異**。差異主要體現在**小時級負載預測的絕對準確度**。

## 🔑 關鍵發現與解讀

### 1. Architecture A (純觀測) 是理論天花板，但**無法部署**

- A 的 MAE 比 B 低 **15%** (50.7 vs 59.7)，這就是**預報誤差對下游模型的傷害**。
- 但在真實 day-ahead 場景下，A 是**作弊**：明天 14:00 的觀測在今天 17:00 不存在。
- A 只能用於：**事後重建**、**模型上限基準**、**研究敏感度分析**。

### 2. Architecture B (純預報) 是現行部署但**訓練信號被污染**

- 訓練時 lag 特徵 = 預報值 = 已被天氣模式誤差污染的代理。
- 這讓模型學到的關係是「預報→負載」而非「天氣→負載」。
- 在部署時誤差被「同源吸收」，但代價是**精度下降**。

### 3. Architecture C (混合) 在 holdout 上**幾乎追上 A 的上限**

- C 的 holdout MAE = 54.0 kW，**僅比 A (50.7) 差 6%**，但比 B (59.7) **改善 10%**。
- Day-peak MAE：A=78.6, C=84.9, B=92.4 → C 在尖峰預測上明顯優於 B。
- **這是免費的午餐**：lag 觀測在部署時 100% 可得（已過去），用觀測取代預報只是換 feature 來源，不需要額外資料。

## ✅ 方法論建議：採用 **Architecture C (Hybrid)**

### 為何 C 才是「方法論最嚴謹」的選擇？

| 標準 | A (純觀測) | B (純預報) | **C (混合)** |
|------|----------|----------|----------|
| Day-ahead 可部署？ | ❌ 用了未來觀測 | ✅ | ✅ |
| Train/Test 一致？ | ✅ 但與真實部署不一致 | ✅ | ✅ |
| 訓練信號乾淨？ | ✅ | ❌ (預報誤差污染) | ✅ (lag 用觀測) |
| 對待「過去」的態度 | 用真實觀測 | 用對應時刻的預報 | **用真實觀測（合理）** |
| 對待「未來」的態度 | 用未來觀測 (作弊) | 用預報 | **用預報（必然）** |
| Holdout MAE | 50.7 (最佳) | 59.7 (最差) | **54.0 (次佳)** |
| 部署可行性 | ✗ | ✓ | **✓** |

### 哲學論證

> **「在預測時間 T，所有 t ≤ T 的氣象變數應該用觀測；所有 t > T 的氣象變數只能用預報。」**

這個原則的對應關係：
- t ≤ T 的氣象：已實際發生 → 有 AMeDAS / ERA5 觀測 → **用觀測** ✓
- t > T 的氣象：尚未發生 → 只有 JMA 預報 → **用預報** (沒得選) ✓

這正是 Architecture C 的做法，也是**業界先進的能源/電力預測系統的標準做法** (e.g., ENTSO-E 風電預測、PJM 負載預測)。

## 🔍 兩種日級別 SDR 決策規則的差異（重要！）

論文中應明確區分以下兩種指標，因為它們衡量的是不同層面：

| 規則 | 定義 | C 架構 F1 | 用途 |
|------|------|----------|------|
| **診斷規則** | `daily.max_pred >= P80` | **0.957** | 評估「模型對日尖峰的預測能力」 |
| **操作規則** | `CCRI >= 0.65 (High tier)` | **0.40** | 評估「實際 SDR 發布系統」(保守策略) |

兩者差異說明 **CCRI 門檻過於保守**，會漏掉部分真實高峰日。這是 **CCRI 校準問題**，不是 Architecture 選擇問題（A/B/C 三者在 CCRI 規則下都會偏保守）。

### 後續可行的優化方向（與本次決策正交）
1. 降低 CCRI High 門檻 0.65 → 0.55（提升 Recall，犧牲 Precision）
2. 加入更多歷史 SDR 日的訓練範例（提升 P80 附近的預測精度）
3. 改用 quantile regression 直接預測 P80 機率
